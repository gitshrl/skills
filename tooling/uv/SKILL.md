name: uv
description: Manage Python projects, dependencies, scripts, and tool installs with uv. Use for any Python dependency work, virtualenv creation, lockfile change, script execution, or Python version pinning.
---

uv replaces pip, pip-tools, pipx, virtualenv, pyenv, and poetry with one tool.

## Use it when

The project has a `uv.lock`, or a `requirements*.txt` with a `# This file was autogenerated by uv` header, or nothing at all and you are starting fresh.

**Do not** use it against a project managed by something else: a `poetry.lock` means poetry, a `pdm.lock` means pdm. Use the tool the project already committed to.

## Commands

Never call `pip` directly and never activate a venv by hand. `uv run` resolves the environment itself.

```bash
uv add <pkg>                  # add a dependency, updates pyproject + lock
uv add --dev <pkg>            # dev-only
uv remove <pkg>
uv sync                       # make the venv match the lock exactly
uv sync --locked              # CI: fail if the lock is stale, never resolve
uv run <cmd>                  # run inside the project env
uv lock                       # re-resolve
uv lock --check               # verify the lock matches pyproject
```

`uv add` edits `pyproject.toml` and the lock together. Editing `pyproject.toml` by hand and running `uv sync` also works, but the two must never drift.

## Scripts

A standalone script declares its own dependencies inline (PEP 723) instead of needing a project:

```bash
uv init --script analyze.py --python 3.13
uv add --script analyze.py httpx rich
uv run analyze.py
```

This is the right shape for one-off tooling. No venv to create, no requirements file to maintain, and the script stays runnable by itself.

## Tools

```bash
uvx ruff check .              # run a tool without installing it
uv tool install ruff          # install it on PATH
```

`uvx` is the pipx replacement. Prefer it for anything invoked once.

## Python versions

```bash
uv python install 3.13
uv python pin 3.13            # writes .python-version
```

uv downloads interpreters itself; the system Python is irrelevant. On PEP 668 systems (Debian/Ubuntu with an externally-managed environment) this is the reason uv works where `pip install` is refused.

## Pitfalls

- **Commit `uv.lock`.** For applications it is the reproducibility guarantee. For libraries, commit it too — it pins the dev environment without constraining consumers.
- **`uv sync` deletes what is not in the lock.** A package installed ad hoc disappears on the next sync. Add it properly.
- **`uv sync --locked` in CI, `uv sync` locally.** The former fails loudly on a stale lock instead of silently resolving a different tree than the one reviewed.
- **`uv pip install` exists but is an escape hatch.** It writes to the venv without touching the lock, so the next sync reverts it. Reach for `uv add`.
- **uv is pre-1.0 but production-stable.** Its own docs say so; minor bumps carry breaking changes. Pin the version in CI.
